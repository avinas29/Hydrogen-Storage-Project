Target leakage, explained simply
Suppose you want to predict ΔH, and one of your inputs is ΔS. In HydPARK, ΔS was calculated as \(R\ln P + \Delta H/T\) from ΔH and one (T, P) point. So if the model knows ΔS, T and P, it can recover ΔH exactly. It would score a near-perfect error, but for a new alloy you never have ΔS in advance, so the model would be useless. The fix: no thermodynamic, pressure, temperature or capacity value is allowed as an input. Only the chemical formula. The feature-building script checks this automatically.
Why the overlap kills "external validation"
A common idea is: train on Purdue, test on HydPARK. But HydPARK copied most Purdue values from the same papers. Testing on them is like setting an exam with the questions the student already studied: a high score proves memory, not understanding. So the project uses one combined dataset with grouped cross-validation instead (Part 5). It also uses the overlap usefully: where two sources report the same composition independently, they differ by ≈ 2.2 kJ/mol. That is the measurement scatter, the best error any model can hope for.

3.3Building the modelling dataset Report §3.3

  1. Parse every formula with pymatgen into atomic fractions (LaNi₅ → La 0.167, Ni 0.833). The rounded fractions form a composition key, so "LaNi5" and "La1Ni5" are recognised as the same alloy.
  2. Keep one row per composition. If Purdue has a single-plateau value, use it; otherwise use the median of the HydPARK values.
  3. Leave out (but keep in the files, flagged): pseudo-element alloys (Mm, Vf: formula not defined), multi-plateau entries (one ΔH doesn't describe them), suspected entry errors, entries the Purdue curators had excluded.
  4. Store with each row: the source of the value, the spread between sources, the quality flags.

Result: 725 compositions (276 with Purdue values, 449 with HydPARK values): AB₂ 401, AB₅ 116, SS 59, AB 40, Mg 35, MIC 33, and a few small groups.

Defend
Q3.1Why didn't you train on one dataset and test on the other?

Because 248 of the 288 parseable Purdue compositions are in HydPARK, mostly with identical values copied from the same papers. The test would measure memorisation of shared records, not generalisation. I used grouped cross-validation on the combined set instead.

Q3.2Why not use ΔS as an input? It's physically related to ΔH.

In HydPARK, ΔS was back-calculated from ΔH and one (T, P) point, so it contains the answer: that's target leakage. And for a new alloy ΔS is unknown anyway. The model's purpose is to estimate ΔH from the formula alone.

Q3.3How did you choose between conflicting values for the same alloy?

Purdue single-plateau value first (it has clear provenance and was checked against the toolbox's own code), otherwise the HydPARK median. The spread between sources is stored so it can be examined; 112 compositions with differing values have a median spread of 1.6 kJ/mol.

Q3.4Did you delete bad data?

No. Every record is kept and flagged. Flags decide what goes into the ML union, the screening data-quality gate and the evidence class. The raw files are untouched.

Q3.5Why exclude mischmetal alloys from the ML set but include them in screening?

Mischmetal is a variable mixture of rare earths, so its exact composition, and therefore its descriptors, cannot be computed. Screening uses only measured properties (ΔH, ΔS, capacity), which exist for those alloys, so they can be screened.

Q3.6Is 725 compositions enough for machine learning?

It is small, which is why I used a random forest (works well on small tabular data), small hyperparameter grids, grouped and nested cross-validation, and simple baselines. It is enough to learn within-family trends (AB₅, AB₂), not enough to learn rare families. The leave-family-out test shows this.

Q3.7How did you know H/M meant "per formula unit"?

By reading the toolbox's MATLAB loader (ReadThermo.m) and checking the value ranges. The Excel export's legend says "per metal atom", which is wrong.
