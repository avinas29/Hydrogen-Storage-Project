Part 7The software platform

Report: §6.3; code in app.py and src/app/

The app ("METAL HYDRIDE AI") is the visible part of the project. Know what each page does, what happens under the hood when you click, and have a short demo ready.

Understand

7.1Architecture

The app computes nothing of its own. Every ΔH comes live from the saved random forest, and every thermodynamic number from the same Van't Hoff functions used in the report. The engines contain no user-interface code, so they can be tested without a browser.

7.3What happens when you press "Predict"

  1. Parse the text (e.g. "LaNi4.2Al0.8") into elements and amounts; reject invalid input with a message.
  2. Normalise to atomic fractions and build the composition key.
  3. Featurise: compute the 38 descriptors (Part 4), using the same code as in training.
  4. Predict ΔH with the saved random forest → 38.69 kJ/mol.
  5. Distance: L1 distance to all 725 training alloys → nearest 0.016.
  6. Interval: look up the calibration bin → [34.3, 41.6]; domain check (≤ 0.15) → in domain.
  7. Warnings: unseen element? already in training (then the value is in-sample)? outside domain?
  8. Van't Hoff estimate with the assumed family-median ΔS, labelled as an estimate.

7.4Discovery Lab and Requirement Designer

Discovery Lab: choose a template (TiFe₁₋ₓMnₓ; Ti–Zr–Mn–Cr or Ti–Cr–Mn Laves; La–Ni–Al, La–Ni–Sn, La–Ce–Ni–Al AB₅; V–Ti–Cr BCC) or free fractions, set ranges and step. The generator builds a reproducible grid and removes duplicates. A candidate is rejected if it has unseen elements, lies outside the domain, or if even the optimistic end of its temperature band misses the target. Survivors are ranked. All outputs say: ΔH predicted, ΔS assumed, capacity not predicted, candidates only.

Requirement Designer: Step 1 application type (5 presets), 2 environment (ambient range, heat source), 3 hydrogen needs (kg, delivery pressure, flow), 4 optional limits (mass, volume, pressures, heating power), 5 weights, 6 review, 7 results. It derives the operating conditions: delivery temperature = heat-source temperature if any, else the coldest ambient; hottest bed temperature; charging temperature (cooling water or hottest ambient). Then it evaluates every measured material.

7.5Testing, and a bug found while writing the report

77 automated tests check parsing, consistency with the training pipeline, the generator, constraints, scoring, Pareto fronts, evidence classes, export and a headless run of every page. While writing the report, reviewing the demo output showed that unranked "insufficient evidence" materials were included in the Pareto computation and could dominate the ranked ones. In the industrial scenario this made the front among ranked materials appear empty. The fix computes the front among ranked materials only, and a new test guards it. Rankings did not change.

Defend
Q7.1Does the app use the same model as the report?

Yes, the identical saved random forest, packaged unchanged. A manifest stores SHA-256 hashes of the model files, and a test checks that the app's predictions match the training pipeline.

Q7.2Why Streamlit?

It turns Python analysis code into an interactive web app quickly, so the same tested engine functions serve the report and the app. For a research prototype that matters more than a custom front end.

Q7.3How do you know the app's numbers are right?

The engines are separate from the interface and covered by 77 tests, including consistency between the app predictor and the training pipeline. All thermodynamics use the same Van't Hoff functions as the report, and the demo outputs were regenerated and compared after the Pareto fix.

Q7.4What stops a user from trusting a bad prediction?

Every prediction shows its interval and the distance to the nearest known alloy; outside the domain it is labelled OUTSIDE DOMAIN with the typical error at that distance; training alloys are flagged as in-sample; unseen elements trigger a warning; Lab outputs are always labelled as candidates.
